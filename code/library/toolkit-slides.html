Let's read them.

Every mission program we write this season starts by borrowing from one file: code/library/toolkit.py. It knows how to drive a distance, turn an angle, and run an attachment. You do not have to memorise it. You have to be able to open it, find the line that is wrong, and change it.

By the end of this you will know what every part of that file does, and you will have found three real bugs in it.

Assumes nothing. You have never written Python before.

The point of it

Write "drive straight" once, not fifteen times

We have 15 missions. Every one of them needs to drive forward and turn. If each program writes its own driving code, we end up with 15 slightly different versions of "drive straight" — and when the robot curves, we have to find out which one is broken.

Without a toolkit

# mission 3
motor_pair.move_for_degrees(
    PAIR, 391, 0, velocity=500)

# mission 7 — same idea, retyped
motor_pair.move_for_degrees(
    PAIR, 390, 0, velocity=480)

# mission 11 — and again
motor_pair.move_for_degrees(
    PAIR, 392, 0, velocity=500)

With the toolkit

# mission 3
await drive_cm(30)

# mission 7
await drive_cm(30)

# mission 11
await drive_cm(30)

Fix driving once and all 15 missions get the fix. That is the whole deal.

This is the same rule as the robot itself: one base that never changes, many attachments. One toolkit, many missions.

Settings: the numbers that describe our robot

A name in CAPITAL LETTERS means "this is a setting, set once at the top, and the rest of the file reads it". Put them all together and changing the robot means changing one block, not hunting through 385 lines.

  1. Ports say which socket each motor is plugged into. Move a cable, change one line here, and everything else still works.
  2. WHEEL_D_MM is how far across a wheel is, in millimetres. Every distance the robot drives depends on this one number.
  3. TRACK_W_MM is the gap between the two drive wheels, measured middle to middle. Every turn depends on this one.
  4. ACCEL / DECEL are how hard it speeds up and slows down.
  5. DEBUG is a switch. True prints what the robot is thinking while it drives. Set it False at a competition.

Important: these two measurements are last year's robot. Before we trust any distance this season, we measure our own wheels and our own track width and type them in here.

The one big idea

The motor has never heard of centimetres

You want to move 30 cm. The motor only understands one thing: turn my shaft this many degrees. A full turn is 360 degrees. So the whole job is converting a distance into a number of degrees — and the bridge between them is the wheel.

Lines 50 to 55 · Read it slowly

Your first function, one line at a time

def _cm_to_deg(cm: float) -> int:
    """Convert distance (cm) to motor degrees."""
    effective_wheel_d = WHEEL_D_MM * CALIBRATION_SCALE
    circ_mm = pi * effective_wheel_d
    rotations = (abs(cm) * 10.0) / circ_mm
    return int(round(rotations * 360.0))
_cm_to_deg(30)
→ circ_mm = 3.14159 × 88 = 276.5
→ rotations = 300 ÷ 276.5 = 1.085
→ degrees = 1.085 × 360 = 391
  1. def means "I am about to teach the robot a new word". The word is _cm_to_deg.
  2. (cm: float) is what you have to hand it. float means a number that can have a decimal point. You can ask for 30 or for 30.5.
  3. -> int is what it hands back: a whole number. Motors count in whole degrees.
  4. The """ line """ is a docstring. A note to the next human. The robot ignores it.
  5. circ_mm is the wheel's circumference. Pi times the diameter, exactly like the last slide.
  6. abs(cm) * 10.0 turns centimetres into millimetres, because the wheel was measured in millimetres. abs throws away a minus sign, so backwards works too.
  7. return hands the answer back to whoever asked.

Everything else in this file is that: take what a human means, turn it into what a motor understands.

Lines 58 to 64

A turn is just a drive round a small circle

When the robot spins on the spot, each wheel drives round a circle. The circle's width is the gap between the wheels — TRACK_W_MM. Turning the robot 90 degrees means driving each wheel a quarter of the way round that circle. Same maths as before, different circle. 

def _robot_deg_to_wheel_deg(robot_deg) -> int:
    turn_circ_mm = pi * TRACK_W_MM
    travel_mm = (abs(robot_deg) / 360.0) * turn_circ_mm
    effective_wheel_d = WHEEL_D_MM * CALIBRATION_SCALE
    wheel_rot = travel_mm / (pi * effective_wheel_d)
    return int(round(wheel_rot * 360.0))
Turn the robot 90°
→ turn circle = 3.14159 × 143 = 449.3 mm
→ a quarter of it = 112.3 mm of wheel travel
→ that is 146 motor degrees

Robot degrees and motor degrees are different things. 90 of one is 146 of the other.

Measure the track width badly and every turn is wrong by the same percentage, all season. It is worth measuring twice.

A naming rule

Why some names start with an underscore

_cm_to_deg, _yaw_deg, _wrap180. That leading underscore is a message from one programmer to another: this is machinery, not a button. It is Python's way of saying "for use inside this file only".

NameMeaningDo you call it from a mission?
drive_cmA move you ask for.Yes. This is the point of the file.
turn_degA move you ask for.Yes.
_cm_to_degMaths that drive_cm uses.No. Let drive_cm use it.
_yaw_degReads the gyro and divides by 10, because the hub reports tenths of a degree.No.
_wrap180Folds any angle back into the range −180 to 180, so 350° becomes −10°.No.

Nothing stops you calling one. Python will not tell you off. It is a convention between people, and following it is how you write code someone else can read.

The two strange words

async and await, explained once

Nearly every move in this file starts with async def, and every time you call one you must write await. Forget the await and the robot will skip the move entirely — no error, no movement. It is the single most common mistake. 

async def drive_cm(cm, velocity=500):
    ...

# in your mission:
await drive_cm(30)      # drives, then continues
drive_cm(30)            # does nothing at all

# at the very bottom of a mission file:
runloop.run(main())

Rule: if the definition says async def, the call says await. Every time.

  1. Driving takes time. A 30 cm move might take a second. The program has to wait for it.
  2. await means "wait here until this finishes, then carry on". Without it, Python builds the job and never starts it.
  3. async def marks a function that can be waited on. You only need it on functions that take time.
  4. runloop.run(main()) is the starter motor. It takes your main function and actually runs it. One line, at the very bottom, in the mission file.

Why bother? Because waiting like this lets the hub keep reading the gyro while the wheels turn. That is exactly what gyro driving needs.

Lines 127 to 150 · The simple drive

drive_cm: count the degrees and go

async def drive_cm(cm: float,
                   velocity: int = 500,
                   stop_mode: int = motor.BRAKE,
                   acceleration: int = ACCEL,
                   deceleration: int = DECEL):
    _reset_yaw(0)
    deg = _cm_to_deg(cm)
    vel = velocity if cm >= 0 else -velocity
    await motor_pair.move_for_degrees(
        PAIR,
        deg,
        0,          # steering 0 = straight
        velocity=vel,
        stop=stop_mode,
        acceleration=acceleration,
        deceleration=deceleration
    )
  1. Those = 500 bits are defaults. Write drive_cm(30) and you get velocity 500 free. Write drive_cm(30, velocity=200) to go slower. You only name what you want to change.
  2. deg = _cm_to_deg(cm) — the conversion from the last slides. 30 becomes 391.
  3. The if / else on one line reads exactly as it sounds: use velocity if the distance is positive, otherwise use minus it. That is how drive_cm(-20) reverses.
  4. steering = 0 means both wheels the same. Straight. 100 would mean spin one way, −100 the other.
  5. stop=motor.BRAKE means stop hard at the end rather than rolling on.

This version trusts the wheels completely. If one wheel slips on the mat, it never finds out — it counted the degrees, so as far as it knows the job is done.

The problem

Counting degrees is not the same as going straight

One wheel grips slightly better than the other. A tyre is slightly softer. A heavy attachment leans on one side. The motors both turn 391 degrees and are perfectly happy — and the robot arrives somewhere it should not be, pointing the wrong way. Small at 30 cm. Enormous by the end of a run.

drive_cm_gyro is a loop that runs 60 times a second

Now the real lines are readable

while True:
    traveled = _avg_deg()
    if traveled >= target_deg:
        break

    yaw_now = _yaw_deg()
    yaw_err = _wrap180(yaw_now)

    if dir_sign < 0:

    if abs(yaw_err) <= deadband_deg:
        raw_steer = 0
    else:
        raw_steer = round(yaw_err * kp)
        ...

    await runloop.sleep_ms(15)
  1. while True: means "keep doing this forever". The only way out is the break.
  2. _avg_deg() asks both wheels how far they have turned and averages the two.
  3. break jumps out of the loop the moment the distance is reached.
  4. yaw_err is how many degrees off straight we are. Because the gyro was zeroed, the reading is the error.
  5. if dir_sign < 0 flips the correction when reversing. Steer left going backwards and you would push further off, not back.
  6. deadband means "close enough". Under 0.1°, do nothing, so the robot does not twitch constantly.
  7. sleep_ms(15) waits fifteen thousandths of a second before checking again. That is roughly 60 checks a second.

Lines 163 to 170 · The dials

Five numbers you will spend a whole session tuning

There is no correct value for these. There is only the value that works on our robot at this speed. Change one at a time, run it five times, write down what happened.

SettingWhat it doesToo smallToo big
kp How hard to correct. The error is multiplied by this. Drifts wide and never quite comes back. Weaves left and right past the line, like a snake.
velocity Driving speed, in degrees per second. Slow. Costs match time. Wheels slip and corrections arrive too late.
deadband_deg How close counts as straight. Twitches constantly over nothing. Ignores a real error and drifts.
steer_rate_limit How fast the steering is allowed to change between checks. Jerky. Corrections slam in. Smooth but slow to react.
steer_limit The biggest correction allowed at all. Never above 100. Cannot recover from a real knock. One bad reading spins the robot.

Three combinations from last season are written in a comment above the function: 600 / kp 2.8, 500 / kp 2.6, 400 / kp 3.2. Notice the pattern — slower driving needed a bigger kp.

Those numbers came off a different robot with different wheels and a different weight. Start from them, do not trust them.

Lines 79 to 102

When 30 cm is not 30 cm

Tell it to drive 300 cm and measure what actually happened. It went 319. The tyre squashes, the mat gives slightly, and the maths is a fraction off. Rather than re-do every number in every program, we tell the file one correction and it applies everywhere. 

def calibrate_wheel_diameter(commanded_cm,
                             measured_cm):
    global CALIBRATION_SCALE
    if commanded_cm == 0:
        return CALIBRATION_SCALE
    CALIBRATION_SCALE = measured_cm / commanded_cm
    return CALIBRATION_SCALE
Asked for 300 cm, it drove 319 cm
→ scale = 319 ÷ 300 = 1.063
→ the file now pretends the wheel is
    88 × 1.063 = 93.6 mm across
→ bigger wheel → fewer degrees → shorter drive
  1. global means "change the real setting at the top of the file, not a private copy". Without that word the correction would be forgotten the instant the function ended.
  2. The if guard catches divide-by-zero. Nobody calibrates against a commanded distance of zero, but the code should not crash if they do.
  3. Went too far → scale above 1 → next time it drives less.
  4. Fell short → scale below 1 → next time it drives more.
  5. Every surface is different. Last season's file has one scale for the competition mat and a different one, commented out, for a hardwood floor.

Do this on the real mat, over a long distance. Errors are easier to see over 300 cm than over 30.

Lines 349 to 385

Attachments: one motor, on its own

Driving uses motor_pair, because two wheels must move together. An arm or a lift is a single motor, so it uses motor instead. Same idea, simpler. 

async def run_attachment_deg(which_port,
                             degrees,
                             velocity=300,
                             stop_mode=motor.BRAKE):
    if degrees > 200:
        return
    await motor.run_for_degrees(
        which_port, degrees, velocity, stop=stop_mode)


async def timed_attachment(which_port,
                           velocity=400,
                           ms=250,
                           stop_mode=motor.BRAKE):
    await motor.run_for_time(
        which_port, ms, velocity=velocity, stop=stop_mode)

In a mission: await run_attachment_deg(attachment1, 90)

  1. which_port is handed in, so one function drives either attachment motor. Pass attachment1 for port C or attachment2 for port D.
  2. run_for_degrees for anything that has a position: lift the arm 90 degrees, and it lifts the same amount every run.
  3. run_for_time for pushing against something. If the arm is jammed against a model, degrees will never be reached, but 250 milliseconds always ends.
  4. nudge_cm and micro_turn_deg at the end of the file are tiny 1.5 cm and 3° moves for settling into a model.

Look hard at that if degrees > 200. We come back to it in two slides.

Your first program

Everything above, in nine lines

This is a whole mission program. It uses the toolkit for every move and contains no maths of its own. That is what a good mission file looks like. 

from library.toolkit import (
    init_robot, drive_cm_gyro, turn_deg,
    run_attachment_deg, attachment1)
import runloop


async def run():
    await init_robot()            # pair the motors, zero the gyro
    await drive_cm_gyro(45)       # out to the model
    await turn_deg(90)            # face it
    await run_attachment_deg(attachment1, 120)
    await drive_cm_gyro(-45)      # straight home


runloop.run(run())
  1. init_robot() first, always. It pairs A and E as one drive unit and zeroes the gyro. Skip it and nothing drives.
  2. Every line has await. Each move finishes before the next one starts.
  3. Negative distance reverses. No separate function needed.
  4. runloop.run(run()) at the bottom starts it.
  5. The comments say why, not what. Anyone can see it drives 45 cm. Only you know it is going to the model.

One catch: the SPIKE App cannot follow that import when you upload. Before it runs on the hub, paste the whole toolkit above the import line. Annoying, and written up in code/missions/README.md.

The real lesson

This file has bugs in it right now

Inherited code is not holy. It was written fast, on a deadline, by people like us. Three of these are sitting in the file today, and you can find them by reading. Reading code carefully beats testing code hopefully.

WhereWhat is wrongWhat happens to you
turn_deg_gyro
line 301		 It works out turn_rate and then never sends it to the motors. The line that starts them is missing. The robot sits still. The angle never changes, so the loop never reaches its target and the program hangs. Use turn_deg instead until someone fixes it.
run_attachment_deg
line 357		 if degrees > 200: return quietly does nothing at all when you ask for more. You ask for 360 degrees, get silence, and blame the motor. Either raise the limit or make it complain.

line 115		 It takes a default_speed and never uses it. You set init_robot(default_speed=200), expect a slow robot, and get a fast one.
